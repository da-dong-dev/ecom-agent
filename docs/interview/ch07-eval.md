## 1. 架构：快慢两条回路 + 评测门面

```
                 POST /api/eval/chat（非流式）
                          │
          ┌───────────────┴────────────────┐
          │                                │
  eval_e2e.py 快回路                 EvalFlow 慢回路
  确定性、无 judge                   judge 质量分、有方差
  路由/字段/金额/动作/引用/泄露        correctness/relevance/faithfulness/context
  几十秒，每次改代码跑               阶段验收、版本对比
```

**为什么要有 `/api/eval/chat`**：

- 生产 `/api/chat` 是 SSE 流式；EvalFlow 要普通 JSON 请求-响应；
- 让平台适配 SSE 成本高，还容易把评测逻辑和生产逻辑混在一起；
- 门面默认关闭（`ENABLE_EVAL_API=false` → 404），生产行为一点没动。

**为什么要两条回路**：

| 回路 | 工具 | 判什么 | 什么时候跑 |
|---|---|---|---|
| 快回路 | `eval_e2e.py` | 路由、字段、退款资格/金额、动作、回答要点、检索 id、是否泄露提示 | 每次改代码 |
| 慢回路 | EvalFlow | answer correctness / relevance / faithfulness / context 类指标 | 阶段验收、版本对比 |

**run 快照**：模型、prompt 版本、`kb_version`、数据集哈希；没有快照，两个 run 的数字不可比。

## 3. 44 条评测集：7 个桶

| 桶 | 条数 | 测什么 |
|---|---|---|
| B1 知识 | 10 | 政策/商品问答、检索与引用 |
| B2 数据 | 8 | 订单、物流、库存、价格 |
| B3 规则 | 8 | 退款 9 状态流水线 |
| B4 边界 | 6 | 定制、拆封、超期、部分退 |
| B5 异常 | 4 | 查不到、缺信息、异常输入 |
| B6 对抗 | 4 | 注入、越权、混合意图 |
| B7 转人工 | 4 | 投诉、赔偿、情绪升级 |

**怎么来的**：385 条外部模型候选 → 58 条 shortlist → 人工审核成 44 条。
每条带 gold：期望路由、退款资格/金额、动作、回答要点、检索 id；标 `dev/test`。

**纪律**：

- `test` 不参与调参；被污染过的旧题移到 `eval_v1_dev_archive.yaml`；
- `expected_output` 支持 `|` 任选，避免 judge 把“A 或 B”误判成缺要点；
- 没有检索证据的样本不写 context / recall / hit@k 行——“不适用”不是 0。

**边界（要主动说）**：44 条能覆盖 7 类问题，但每桶 n 很小；它保证“有尺子”，
不保证“统计上代表所有用户”。

## 4. 指标语义与覆盖率

| 指标 | 白话 |
|---|---|
| hit@3 | 正确答案所在资料块，有没有出现在前 3 条 |
| MRR | 正确答案排得越靠前越高；第 1 是 1，第 5 是 0.2 |
| context_precision | 检索回来的资料里，有多少真正相关 |
| context_recall | 应该找到的资料，找到了多少 |
| faithfulness | 回答里的说法，是否都能在检索资料里找到依据 |
| answer_relevance | 回答是否切题 |
| answer_correctness | 回答是否正确覆盖 gold 要点 |

**覆盖率**：context / faithfulness / recall / hit@k / MRR 只对 B1 的 10 条适用；
B2–B7 没有检索证据，不适用就不写行。run-01 显示 `10/44` 是旧代码给所有样本写 NULL 行
造成的展示问题，run-02 起是 `10/10`；NULL 本来就不参与均值。

**judge 方差**（#32 / #33 / #34，同批 44 条、同代码）：

| 指标 | 三轮均值 | 极差 |
|---|---|---|
| answer_correctness | 0.9977 | **0.45pp** |
| answer_relevance | 0.8867 | **3.86pp** |
| context_precision | 0.885 | 2.5pp |
| recall / context_recall / faithfulness | 1.000 | 0 |

- 44 条里只有 **20 条（45%）** 三次回答逐字相同（temperature=0.2）；
- 波动集中在 B5–B7 兜底话术：4 条**同一回答**被 judge 判出 0.3–0.9；
- 结论：**correctness / recall 的提升可信；relevance 的 +0.0431 在噪声带内，
  不能归因于 FAQ**；context_precision 的 −0.04 也不能下结论。

## 5. 阈值扫描：为什么是 0.55

机械闸只有一个 top1 阈值，**做不到双零**：

- 0.55 时：可答 42/42 放行，但负样本只拦住 10/11，**误放率 9.1%**；
- 漏点例子：`能分期付款吗` top1 = `member#积分规则` **0.572**，机械闸放行；
- `FB-30 保修多久` top1 = `products#辅食机 FB-30` **0.566**，放行是对的——
  两条分数只差 0.006，单阈值分不开。

**语义闸**：

```
top1 < 0.55          → weak（不调模型）
top1 >= 0.60         → strong（不调模型）
0.55 <= top1 < 0.60  → 边界带：调一次证据自评
                        sufficient=true  → strong
                        false/超时/异常 → weak（fail-closed）
```

- 自评超时 **3s**、**不重试**；单次约 **1.1s**；
- 只影响边界样本，C/E 路径不变；
- 语义闸把“误拦 0 + 误放 0”的区间扩到 **0.53–0.56**，0.55 落在中部，
  两侧余量约 0.01–0.02；机械闸最优折中是 0.58（误拦 2.4%、误放 0.0%）。

**关键纪律**：阈值只用确定性指标（放行/拦住）调，不用 relevance 均值调。
relevance 的抖动比阈值带来的差异还大。

## 6. 退款困难组：dev 10 + held-out 15

| 数据集 | n | 模型 | 模型 95% CI | 规则 | 流水线 |
|---|---:|---:|---|---:|---:|
| 简单组 | 20 | 19/20 | 76%–99% | 20/20 | 19/20 |
| 困难组 dev | 10 | **10/10** | 72%–100% | 3/10 | 8/10 |
| 困难组 held-out | 15 | **15/15** | 80%–100% | 6/15 | 13/15 |

held-out 分 5 类 × 3：规则顺序 / 字段粒度 / 数据缺口 / 语义模糊 / 多轮补充。

**为什么流水线低于模型**：

- T04/T05 是**字段粒度**问题：`condition_ok` / `packaging_opened` 只有订单级，
  模型能按“要退的那件”判对，规则会用整单字段否决；
- 模型判对、规则判错 → compliance 分歧 → 转人工；
- 这是**安全网的代价**，不是模型退化，也不是错退。

**held-out 的边界**：

- 运行后修正过 T01/T03 的 gold（与 B07 / 规则表对齐），且修改前已看过结果；
- 规则顺序组因此降为参照组（3/3），其余 4 组 12/12；
- **15/15 不能当严格盲测准确率**，只能叫 held-out 验证；
- 后续再改 prompt 或 gold，必须换新一批没看过的样本。

## 7. 三个踩坑故事（STAR）

### 7.1 评测脚本用真实时钟算 7 天窗口

- **S**：固定日期的 gold set，Ch03 验收是 7/10，后来重跑数字对不上；
- **T**：`run_judge` 没把 case 的 `now` 传给 judge，模型用运行当天算 7 天窗口；
- **A**：把 case 的 `now` 传进 judge，固定时间锚点；
- **R**：Ch03 的 7/10 不可复现；修完 prompt 后 dev 为 10/10。

**可讲**：「时间敏感评测必须冻结时间；否则样本会随运行日期漂移，历史报告不可比。」

### 7.2 B07 与 H06/T01 的 gold 冲突

- **S**：确定性回归 B07 掉到 43/44；
- **T**：B07/seed 1108 规定“已发货未签收 + 定作 → `reject_then_refund`”，
  H06/T01 的 gold 却写成 `not_applicable`；
- **A**：以规则表/B07 为准，统一 H06/T01/T03，并恢复 prompt 的状态优先级；
- **R**：B07 回归消除；held-out 规则顺序组成为参照组。

**可讲**：「评测集本身也会错。gold 和规则表冲突时，要做交叉校验，不能只改 gold 让分数变好。」

### 7.3 把 judge 噪声当成 FAQ 的收益

- **S**：run-02 的 relevance 从 0.8614 升到 0.9045，看起来 FAQ 有效；
- **T**：同一批样本连跑 #32/#33/#34，看什么都不改时能差多少；
- **A**：三轮 relevance 为 0.9045 / 0.8659 / 0.8898，极差 **3.86pp**；
  注入样本回答逐字相同，judge 判过 0.0 / 0.0 / 0.9；
- **R**：只把 correctness / recall / context_recall 的提升算作 FAQ 收益；
  relevance 的 +0.0431 在噪声带内，不能归因。

**可讲**：「先测噪声，再谈提升。同一个回答 judge 能差 0.6，单次 run 的 ±2–4pp 不能当结论。」

## 8. 追问清单

| 问题 | 答题要点 |
|---|---|
| 为什么不直接测 `/api/chat`？ | 它是 SSE；评测要 JSON、要隔离、要快照，门面默认关闭 |
| 为什么确定性脚本和 EvalFlow 都要？ | 硬约束不能交给 judge；质量分需要 judge。快回路每次跑，慢回路阶段跑 |
| 为什么是 44 条，不是 385 条？ | 44 条覆盖 7 类；扩样本解决覆盖，不解决 judge 噪声。先有尺子再加长 |
| 为什么 context 指标只覆盖 10 条？ | 只有 B1 有检索证据；不适用不写行，不能当 0 混进分母 |
| correctness 0.9977 为什么 relevance 只有 0.89？ | 两个 judge 判的东西不同；relevance 对“转人工/拒答”天然低分 |
| 为什么 B5–B7 relevance 低不算问题？ | 它们是安全兜底；通用 judge 把“没回答”当“不相关”，要看路由/动作 |
| 为什么机械闸不能双零？ | 0.566 和 0.572 只差 0.006，单阈值分不开“话题近但没答案”和“确实有答案” |
| 语义闸为什么只处理 [0.55,0.60)？ | 0.60 以上不值得再问；0.55 以下大概率 weak；只有边界可能翻转 |
| 为什么定 0.55？ | 语义双零区间 0.53–0.56，0.55 在中部；两侧余量约 0.01–0.02 |
| 为什么退款流水线低于模型？ | `condition_ok` / `packaging_opened` 是订单级；模型对、规则错 → compliance 分歧 → 转人工 |
| held-out 15/15 能写 100% 吗？ | 不能；n=15 的 95% CI 80–100%，且 T01/T03 gold 运行后修正过，不是严格盲测 |
| 为什么要 Wilson CI？ | n 小，点估计不可靠；CI 把样本量翻译成可信范围 |
| judge 方差怎么量化？ | 同代码同数据连跑 3 次；correctness 极差 0.45pp，relevance 3.86pp |
| 阈值能不能用 relevance 调？ | 不能；relevance 噪声比阈值差异大，只用确定性放行/拦住 |
| Ch07 除了测量还改了什么？ | FAQ 15 条、语义证据闸、退款 judge prompt、其他用户订单候选修复 |
| 如果继续做什么？ | 扩盲测样本、judge 3 次取中位数、退款字段拆到件级、独立 safe_handling 指标 |
